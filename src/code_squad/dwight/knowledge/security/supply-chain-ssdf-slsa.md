## Scope

Review of how software is built, its dependencies are chosen and locked, its artefacts are produced and verified, and its CI/CD is secured. Vulnerability status of individual packages is handled in `dependency-triage.md`. This file covers the process controls and the review cues. CI mechanics are reviewed by `darryl`; cite their rules when the issue is pipeline correctness.

## Rules

### SEC-SUPPLY-001 — Dependencies are locked and resolved from known sources

- **Look for:** manifests changed without the lockfile; floating ranges for production dependencies; registries or indexes configured to a non-approved source; mixed public and private registries without namespace controls.
- **Why it matters:** an unexpected version or package enters the build (CWE-494, CWE-829). Dependency confusion (CWE-427) occurs when a public package shares a name with an internal one.
- **Good:** lockfiles committed and used in CI (`npm ci`, locked Gradle or Maven resolution); private package scopes reserved on the public registry.
- **Default severity:** medium; high where a private package name is unclaimed on the public registry.

### SEC-SUPPLY-002 — New dependency review

- **Look for:** new packages with few maintainers, very recent first release, names close to popular packages (typosquatting), install scripts, or unexpected network access.
- **Good:** justify the dependency, check maintenance and ownership, and check for install scripts and binary payloads.
- **Default severity:** medium; high when the package has install scripts and network access.
- **CWE:** CWE-1357 (reliance on insufficiently trusted component), CWE-1104.

### SEC-SUPPLY-003 — Install scripts

- **Look for:** `preinstall`, `install`, `postinstall` in new or changed packages; `prepare` scripts running build steps; CI configured to run lifecycle scripts for untrusted packages.
- **Good:** `npm ci --ignore-scripts` where scripts are not needed, then explicit rebuilds for allowed packages; allowlists for scripts (for example pnpm `onlyBuiltDependencies`).
- **Default severity:** medium; high for network or credential access in scripts.
- **Detail:** `node-react.md`.

### SEC-SUPPLY-004 — CI actions and reusable steps are pinned

- **Look for:** GitHub Actions referenced by mutable tags (`@v4`, `@main`); GitLab includes from unpinned refs; CI templates fetched from branches; third-party actions with broad write permissions.
- **Good:** pin to a full commit SHA; restrict `GITHUB_TOKEN` permissions; review updates.
- **Default severity:** high for untrusted or write-privileged actions; medium otherwise.
- **Cross-reference:** `darryl` rules for GitHub Actions.

### SEC-SUPPLY-005 — Build provenance

- **Look for:** released artefacts without provenance attestation; build environments that the producer does not control; manual builds for release.
- **SLSA reference:** Build L1 requires provenance generated by the build. Build L2 requires a hosted build platform that signs provenance. Build L3 requires the build to be isolated from the job's user-controlled steps. Use the levels as a target maturity, not as a pass or fail gate, unless the project declares a target.
- **Good:** generate provenance in CI (for example the SLSA generator or platform attestations), sign with an identity-bound signature, verify before deployment.
- **Default severity:** low to medium; advisory unless the project sets a target.

### SEC-SUPPLY-006 — Artefact signing and verification

- **Look for:** container images pushed without signatures; deployment pipelines that do not verify signatures; checksum files published next to artefacts without a signature.
- **Good:** sign images and release artefacts with keyless or managed keys; verify at deploy time.
- **Default severity:** medium.
- **CWE:** CWE-345, CWE-347.

### SEC-SUPPLY-007 — SBOM

- **Look for:** no software bill of materials for a released artefact; SBOM generated from an out-of-date source.
- **Good:** generate an SBOM (CycloneDX or SPDX) in the build for each release artefact and store it with the artefact.
- **Default severity:** low to medium.

### SEC-SUPPLY-008 — CI runner and pipeline integrity

- **Look for:** pull-request pipelines with access to secrets from untrusted forks; self-hosted runners shared between projects; build jobs able to modify the pipeline definition used for release.
- **Good:** separate trust levels for PR and release pipelines; ephemeral runners; protected branches for release configuration.
- **Default severity:** high for secret exposure to untrusted code.
- **CWE:** CWE-829, CWE-250.

### SEC-SUPPLY-009 — Vulnerability management process

- **Look for:** no automated dependency update or advisory monitoring; known-vulnerable versions retained in production without an exception record.
- **Good:** scheduled dependency update PRs; advisory alerts; a documented exception process with expiry.
- **Default severity:** low to medium.

### SEC-SUPPLY-010 — Secure development practices (NIST SSDF groups)

- **Look for:** missing controls against SSDF practice groups in the diff area: preparing the organisation (PO), protecting software (PS), producing well-secured software (PW), responding to vulnerabilities (RV).
- **Use:** cite the practice group only as a category. Do not claim SSDF conformance from a diff.
- **Default severity:** advisory.

## How to apply in review

1. For each changed manifest, check that the lockfile changed with it and that the new packages are justified.
2. For each changed CI file, check action and include pinning, permissions, and secret scope. Route pipeline mechanics to `darryl`.
3. For release-related changes, check signing, provenance, and SBOM steps.
4. Cite the manifest or workflow line and the specific control missing.
5. Do not assert that a package is vulnerable here. Use `dependency-triage.md` for that.
